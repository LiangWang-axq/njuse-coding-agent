# 面试问答准备

以下口径全部对应实际代码，答辩时按“现象 → 我的设计 → 为什么这样设计”展开。

1. **为什么不用 LangChain 等框架？**
   题目明确要求重要逻辑自行编写。历史管理、工具执行、输出解析、终止与错误处理都是本项目独立实现的模块，用框架会掩盖这些设计点，也无法在答辩中展开说明。

2. **Agent 整体如何运转？**
   `CodingAgent.run` 是主循环：system 提示 + 用户任务 → 调用模型 → `parse_model_response` 解析动作 → `ToolRegistry` 本地执行 → 工具结果回填历史 → 继续循环，直到模型返回 `final` 或达到 `max_steps`。

3. **上下文如何管理？**
   `ContextManager` 保存完整历史，每次调用模型前由 `prepare()` 生成非破坏压缩视图，共四层、廉价优先：L3 超大工具结果（>12000 字符）先落盘到 `.coding_agent/results/`，视图换成路径+预览；超预算时 L1 裁切中间轮次、L2 把较早工具结果压成一行摘要（最近 2 条不动，0 API）；仍超限才 L4 调用模型生成 `<summary>` 结构化摘要，失败则降级不压缩。另外用模型返回的真实 `usage` 校准“字符/4”的 token 估算，预算判定随对话推进越来越准。

4. **模型输出怎么解析？**
   `parse_model_response` 兼容两种协议：纯 JSON 动作与 OpenAI 原生 `tool_calls`；会容错地从文本中提取首个 JSON 对象；支持一次返回多个工具调用依序执行；连续两次解析失败即终止，防止死循环。

5. **工具如何定义与执行？**
   `tool_schemas()` 集中声明 10 个工具的名称、描述和 JSON Schema 参数；`ToolRegistry` 映射到本地实现；所有文件操作经 `_path` 校验后才执行。

6. **安全性如何保证？**
   所有路径解析后必须是工作区内的相对路径，拒绝绝对路径、盘符、`..` 和 `.env`；`run_tests` 不经 shell，仅允许 `python -m unittest/pytest/compileall`，禁拼接、120 秒超时，可用 `cwd` 指定工作区内相对目录（仍锁定在工作区）；`git_status` 参数固定且只读。

7. **循环如何终止？**
   三层保障：模型返回 `final` 正常结束；达到 `max_steps`（默认 24）强制停止；连续两次输出格式错误立即失败。工具错误不会终止，而是回传模型让其修正。另外系统提示固化收敛规则——测试通过立即返回 `final`、不重复读取已确认文件、验证语法用 `python -m compileall` 而非 `python -c`——从源头防止“重复确认”式无效循环烧掉步数。

8. **API 失败怎么处理？**
   HTTP 429、5xx 与超时按 2s/4s 退避重试（`AGENT_RETRIES` 可配）；其余 4xx 快速失败并输出可读信息；网关不支持 `tools` 参数（400）时自动降级为纯 JSON 协议，兼容不同服务商。

9. **为什么用 OpenAI 兼容接口？**
   模型无关。默认配置 DeepSeek，也可以换成任何兼容 Chat Completions 的服务；客户端只用标准库 `urllib` 实现，无框架依赖。

10. **为什么工具结果用 user 消息回填而不是原生 tool role？**
    既兼容不支持原生 tool role 的网关，也让 JSON 协议与原生协议共用同一套历史结构；原生 `tool_calls` 同样被解析执行，两者效果一致。

11. **一次返回多个工具调用怎么处理？**
    解析层把多个 `tool_calls` 转成有序列表，主循环依序执行并把结果合并回填，单轮最多 8 个，防止异常请求。

12. **文件修改为什么用整体写入 + 精确替换？**
    简单、可控、可审计。`replace_in_file` 要求匹配次数与期望一致，匹配不到或匹配过多都会报错，避免误改；演示任务中用测试失败定位 bug 后精准修改。

13. **为什么测试命令要白名单？**
    执行任意命令风险不可控。白名单只放行 `python -m unittest/pytest/compileall`，无 shell 拼接、无重定向、参数不得越界，保证 Agent 只能验证代码而不能逃逸工作区。

14. **演示任务的 bug 是什么？**
    `demo/tasks/fix_me` 中 `format_total` 缺少人民币符号、`apply_discount` 用减法代替百分比折扣。Agent 先跑测试看到 2 个失败，再读代码、精准替换、重跑测试直到通过并输出 `final`。

15. **已知限制与改进方向？**
   已支持工作区内的会话持久化、列表、指定恢复和确认删除，以及 usage 校准上下文估算；仍可改进：跨工作区会话索引、大结果文件按会话隔离、累计 token/成本展示和只读工具并行执行。

20. **会话如何持久化与恢复？**
    `CodingAgent` 构造时在 `<工作区>/.coding_agent/sessions/` 下创建 JSONL 会话文件，每条消息（用户任务、助手输出、工具结果、纠错反馈）追加后立即 `Session.add` 原子落盘：临时文件 + `fsync` + `os.replace`，崩溃不损坏上次快照。`--resume` 恢复最新会话，`--resume-session` 或 `/resume` 按序号、完整 ID、唯一前缀恢复指定会话，加载时校验 header、丢弃撕裂尾行并把历史重放进 `ContextManager`。`--list-sessions` 或 `/sessions` 展示列表，删除命令确认后只移除选中的 JSONL；删除当前会话会自动开启新会话。

16. **为什么这一步调用了某个工具？**（追问型）
    对任意具体调用，都可以从终端输出的 `[步骤 N] 工具名 -> OK` 回放：它对应主循环的哪一轮、参数是什么、结果如何回填、模型下一步据此做了什么。答辩前建议把演示视频的每一步与 `docs/DESIGN.md` 对应一遍。

17. **流式输出是怎么实现的？**
    `chat_stream` 自行解析 SSE：按行缓冲 `data:` 事件、`[DONE]` 终止；文本 `delta` 直接回调终端逐字显示；原生 `tool_calls` 在流中按 `index` 增量拼接 `id/name/arguments`，结束时 `json.loads` 校验后交给与普通请求相同的 `parse_model_response`。重试只发生在首块数据到达前，避免重复输出。

18. **多轮对话如何保持上下文？**
    `CodingAgent` 持有同一个 `ContextManager`，`run()` 首次调用创建、后续调用复用，用户新消息直接追加，超限时仍走原有压缩摘要；`/new` 调用 `reset()` 清空历史。

19. **为什么终端界面不用 Rich/Textual？**
   保持“仅标准库”的项目卖点。ANSI 颜色 + `ctypes` 开启 Windows VT 处理，非 TTY 或 `NO_COLOR` 时自动去色；斜杠命令与流式渲染都是自研实现，答辩可以展开。

21. **界面有哪些可视化设计？**
   三个层次。一是工具调用多行卡片：工具名、参数、结果摘要分开展示，`run_tests` 失败时直接附输出尾部，方便边演示边解释模型每步做了什么；二是压缩事件实时播报：`ContextManager.prepare` 记录本次触发的压缩层，`on_context` 回调在状态变化时打印 `[上下文] L2 压缩 3 条旧工具结果` 之类提示，把“四层压缩管线”从实现细节变成可见过程；三是 token 用量与预算：每轮结束显示真实 usage（无 usage 时用估算）与预算，`/status` 展示累计压缩统计。全部是纯标准库 ANSI，无第三方 UI 依赖。
